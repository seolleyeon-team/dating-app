# Blind meeting party Firestore audit (2026-09-01)

Target: `projects/seolleyeon-final/databases/(default)` — Standard edition,
Firestore Native, `asia-northeast3`.

## Existing relevant paths

- `users/{uid}`: private account/profile source. Client reads/writes are governed
  by the existing canonical-session allowlists. Blind meeting server code reads
  verification, account state, onboarding gender/lifestyle/campus zones.
- `users/{uid}/friends/{friendUid}`: server-authoritative friendship mirror.
  Party invite creation must verify this document server-side.
- `blindMeetingDna/{uid}` and `blindMeetingDnaDrafts/{uid}`: owner-get only,
  client writes denied. Cloud Functions persist private DNA.
- `blindMeetingApplications/{uid}`: owner-get only, client writes denied. The
  server matcher queries open applications by date.
- `blindMeetings/{meetingId}` and participant/public-profile subcollections:
  meeting participants read; all lifecycle writes are server-only.

## New paths

- `blindMeetingParties/{partyId}`: server-written party surface. Required
  fields are `partyId`, `leaderUserId`, `acceptedUserIds` (1..3),
  `pendingInviteeIds` (0..2), `memberCount`, `canonicalGender`, `status`,
  `rosterVersion`, `completedApplicationUserIds`, `meetingId`, and timestamps.
  Reads are limited to authenticated accepted members. Pending invitees see
  only their invite document until they accept. Client writes are denied.
- `blindMeetingPartyInvites/{inviteId}`: server-written invite. Read is limited
  to inviter/invitee; client writes are denied.
- `blindMeetingPartyMatching/{partyId}`: private derived matching policy. All
  client reads and writes are denied.
- `blindMeetingPartyMemberships/{uid}`: private uniqueness lock preventing one
  account from joining two active parties. All client reads and writes are
  denied.

## Queries to support

- App: direct `get`/`snapshots` by known party and invite IDs.
- App: `blindMeetingParties.where(acceptedUserIds, arrayContains: uid)` to
  recover the current party. Rules authorize only documents containing the
  caller; a collection index on the array field is automatic.
- App: `blindMeetingPartyInvites.where(inviteeUserId == uid).where(status ==
  pending)` for received invitations. Both fields are equality filters, so
  Standard edition index merging is sufficient, but an explicit composite is
  added for deterministic deployment parity.
- Server Admin SDK: ready party/application scans and matching-policy reads;
  rules do not apply.

## Authority and privacy

- The Firebase Auth UID and server reads of users/friends/applications are the
  only authority. No client-provided leader/member/readiness/gender value is
  trusted.
- Party documents expose member IDs and completion state only to the party.
  Effective purpose/alcohol/smoking policy remains in the denied matching path
  so one member cannot infer another member's private DNA.
- All new client writes are denied, avoiding create/update schema-bypass and
  ownership-escalation classes entirely.

Checklist notes:

- Update bypass: no client create/update/delete is allowed on any new path.
- Authority source: authentication UID is compared only with server-written
  resource fields; callable code independently verifies friendship, canonical
  gender, student/account state, capacity, and membership locks.
- Business logic: accepted members can recover/query their team; invitees can
  query their pending invitations without gaining roster access before accept.
- Storage abuse/type safety: all writes use Admin SDK transactions with bounded
  arrays (maximum three accepted, two pending) and sanitized profile strings;
  malformed server documents fail closed in rule predicates/read parsers.
- Identity security: no field-only update permission exists; all writes are
  server-only.
