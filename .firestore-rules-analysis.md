# Firestore Rules compatibility analysis

- Target: `seolleyeon-final`, `(default)`, Standard/Native Firestore.
- Baseline reviewed: the Rules pasted from the Firebase console plus the
  current Flutter, web, Cloud Functions, recommendation-job, and Rules-test
  access patterns in this checkout.

## Active recommendation access paths

- `users/{uid}`: the signed-in user reads their own
  `recommendationPrivacyReady` state. Existing `isSelf(uid)` rule matches.
- `recommendationExclusions/{uid}/targets/*`: the signed-in user lists their
  own exclusions from the server. Owner list/get is required; client writes
  remain denied because callables materialize both directions.
- `blocks/{uid}/targets/*`: the signed-in user lists their own safety blocks.
- `modelRecs/{uid}/daily/{dateKey}/sources/{algo}`: the signed-in user gets a
  single current/previous-day source document. Owner get is required; list and
  all client writes are unnecessary.
- `dailyRecs/{uid}/days/{dateKey}`: server-generated compatibility feed. Owner
  get is allowed even though the current Flutter service still serves
  `modelRecs`.
- `publicProfiles/{candidateUid}`: the app performs direct document gets and
  document listeners for rendered candidates. Authenticated get is required;
  collection list remains denied.

## Authentication access paths

- `sendStudentVerificationEmail` creates `emailLinkTokens/{token}` through the
  Admin SDK. No current client create/update/delete path exists.
- The unauthenticated email-link landing page and the app link handler perform
  one direct get by an opaque token, so `allow get: if true` remains necessary.
  Collection list remains denied.

## Codebase scan notes

- Literal Flutter collection names were compared with Rules match paths.
- `PostService` (`posts`) and `AiSwipeService` legacy `ai_swipes`,
  `ai_sessions`, and `embeddings` paths have no call sites outside their own
  service files. They remain default-denied instead of opening unused client
  storage, especially because embeddings contain private vectors.
- Active community code uses `bamboo_posts`; its like counter must change in
  the same atomic commit as `bamboo_posts/{postId}/likes/{uid}`.

## Compatibility conclusion

- The Kakao privacy Rules match the app's exact document and query shapes.
- No active normal 1:1 recommendation request is denied by these Rules when
  Firebase Auth uid equals the Kakao-backed uid.
- The current app requires that Firebase session bridge before any private
  Firestore access; unauthenticated Kakao-only sessions intentionally fail
  closed.

## Devil's-advocate results

The emulator suite exercised the following classes of attacks against the
final Rules. Unless noted, the attempted request was denied and its normal
owner/participant counterpart was allowed.

1. Public collection/list access: denied for private users, recommendations,
   exclusions, tokens, chats, and meeting state.
2. Unauthorized read/write: denied for cross-user profile, exclusion,
   recommendation, token, notification, block, chat, and meeting paths.
3. Create-then-update bypass: protected fields and unsupported fields were
   rejected by the update allowlists.
4. Ownership hijacking on create: forged `kakaoUserId`, `authorId`, sender ID,
   and participant IDs were rejected.
5. Ownership hijacking on update: participant IDs and protected user fields
   could not be changed.
6. Immutable field modification: protected match/chat/user state transitions
   were rejected.
7. Type juggling: invalid email token timestamps and typed event payloads were
   rejected.
8. Create/update validation mismatch: email-link tokens are server-created and
   cannot be modified by clients.
9. Resource exhaustion: active post/message/report strings have limits;
   existing analytics append paths still warrant a separate size-limit audit.
10. Required-field omission: tested onboarding, events, posts, and chat writes
    were rejected when required fields were absent.
11. Privilege escalation: `role`, `isAdmin`, verification, moderation, and
    login-disabled fields could not be self-assigned.
12. Schema pollution: new fields outside affected-key allowlists were denied.
13. Invalid state transition: match, promise, and meeting client transitions
    outside their allowed states were denied.
14. Path scoping: private media and user-owned nested paths remained scoped.
15. Timestamp manipulation: token timestamp types and server-owned operational
    timestamps remained protected.
16. Negative/overflow counters: non-negative and delta-one counter checks
    rejected direct values.
17. Mixed-content leak: private `users` documents remained owner-only;
    candidates are read through `publicProfiles`.
18. Counter replay: a post like increment without the matching like-document
    transition, and a duplicate increment, were rejected.
19. Orphaned subcollections: sensitive nested paths use UID/participant gates
    independent of trusting a client-owned parent.
20. Query mismatch: the active recommendation app uses direct gets and owner
    target-list queries matching the Rules exactly.
21. Validator review: the new recommendation paths are server-write-only, so
    no client create/update validator is needed; existing client-writable
    collections retain their domain checks and should continue to be audited
    separately as schemas evolve.
